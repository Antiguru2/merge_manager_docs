# Правила оформления документации проекта

Этот документ описывает стандарты и требования к оформлению документации проектов для работы с AI-ассистентом.

## 🎯 Общие принципы

1. **Ясность и понятность** — документация должна быть понятна как AI-ассистенту, так и человеку
2. **Структурированность** — используйте четкую иерархию разделов
3. **Конкретность** — избегайте абстрактных формулировок, предоставляйте конкретные примеры
4. **Актуальность** — поддерживайте документацию в актуальном состоянии
5. **Полнота** — документируйте все важные аспекты проекта

## 📋 Обязательные файлы

### `OVERVIEW.md` — Обзор проекта

**Обязательные разделы:**

#### 1. Название и краткое описание
- Одно-два предложения
- Четко объясняет, что это за проект и зачем он нужен
- Формат: "Название — это [что], которое [зачем]"

#### 2. Тип проекта
- Выберите одну категорию: библиотека, приложение, сервис, инструмент, плагин, фреймворк, расширение
- Укажите основной язык программирования

#### 3. Принцип работы
- Подробное объяснение простым языком
- Опишите архитектуру на высоком уровне
- Укажите основные компоненты и их взаимодействие
- Объясните ключевые концепции
- Длина не ограничена, но стремитесь к краткости

**Требования:**
- Используйте диаграммы, если это помогает пониманию
- Избегайте излишних технических деталей
- Фокус на общей картине, а не на деталях реализации

### `QUICKSTART.md` — Быстрый старт

**Обязательные разделы:**

#### 1. Требования
- Минимальный список зависимостей
- Версии необходимого ПО
- Системные требования (если есть)

#### 2. Установка
- Пошаговая инструкция

#### 3. Первый запуск
- Самый простой рабочий пример

**Требования:**
- Код должен работать "из коробки"
- Пример должен быть максимально простым
- Добавьте пояснения к коду

### `API.md` — Документация API

**Обязательные разделы:**

#### 1. Краткое описание
- Какие технологии используются (REST, GraphQL, gRPC и т.д.)
- Базовый URL (если применимо)

#### 2. Права доступа и авторизация
- Способ аутентификации (API ключ, OAuth, JWT и т.д.)
- Как получить доступ
- Примеры заголовков авторизации

**Пример:**
```markdown
## Авторизация

Используется Bearer Token в заголовке:

\`\`\`
Authorization: Bearer YOUR_API_KEY
\`\`\`
```

#### 3. Список эндпоинтов

**Формат описания каждого эндпоинта:**

```markdown
### `METHOD /path`

Краткое описание того, что делает эндпоинт.

**Параметры:**
- `param1` (string, required) — описание параметра
- `param2` (number, optional) — описание параметра

**Пример запроса:**

\`\`\`bash
curl -X POST https://api.example.com/path \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{
    "param1": "value1",
    "param2": "value2"
  }'
\`\`\`

**Ответ:**

\`\`\`json
{
  "status": "success",
  "data": { ... }
}
\`\`\`

**Коды ответа:**
- `200` — успешно
- `400` — ошибка валидации
- `401` — не авторизован
```

**Требования:**
- Документируйте все эндпоинты

### `CHANGELOG.md` — История изменений

**Формат:**

```markdown
# История изменений

## [Версия] - Дата

### Добавлено (Added)
- Новая функциональность

### Изменено (Changed)
- Изменения существующей функциональности

### Исправлено (Fixed)
- Исправления багов

### Удалено (Removed)
- Удаленная функциональность

### Устарело (Deprecated)
- Функции, которые будут удалены в будущем

### Безопасность (Security)
- Исправления уязвимостей
```

**Требования:**
- Версии располагаются в обратном хронологическом порядке (новые сверху)
- Используйте семантическое версионирование (SemVer): MAJOR.MINOR.PATCH
- Группируйте изменения по категориям
- Будьте конкретны в описании изменений
- Указывайте даты в формате YYYY-MM-DD
- При внесении изменений **НЕ изменяйте** старые логи в CHANGELOG. Просто добавляйте **один новый лог** о текущем изменении в начало файла

### `PLAN.md` — Общий план проекта

**Назначение:**
- Фиксирует общий план проекта на уровне фаз, крупных функциональных блоков и технических направлений
- Показывает общее состояние проекта через отметку выполнения конкретных пунктов
- Используется AI-ассистентом как основная точка для ведения плана

**Обязательная структура:**
- `## Фаза N: Название`
- `### N.M Название блока`
- `## Заметки`

**Рекомендуемый формат наполнения:**
- Используйте фазы верхнего уровня: `## Фаза N: Название`
- Внутри фаз используйте блоки работ: `### N.M Название блока`
- Для конкретных пунктов используйте чекбоксы `- [ ]` и `- [x]`
- Не разбивайте `PLAN.md` на секции `Запланировано`, `В работе` и `Выполнено`

**Требования:**
- `PLAN.md` заполняется и поддерживается AI-ассистентом
- Вносите в него только общий план проекта, а не личные задачи разработчика
- Допускается укрупнённое описание задач, если это помогает видеть общую картину
- Выполнение отражайте изменением чекбоксов, а не переносом пунктов между разделами

### `workspace/tasks/tasks.md` — Задачи разработчика

**Назначение:**
- Содержит личные, операционные и прикладные задачи разработчика
- Используется для повседневной работы над проектом

**Требования:**
- Этот файл заполняется разработчиком
- Не дублируйте сюда общий проектный план из `PLAN.md`
- Допускается свободная детализация задач, если она удобна разработчику

## ⚠️ Работа с файловой структурой

### Правило добавления дополнительных файлов

**ВАЖНО:** Любые добавления файлов помимо стандартных (перечисленных выше) **ТРЕБУЮТ ОБЯЗАТЕЛЬНОГО УТОЧНЕНИЯ** у пользователя!

**Стандартные файлы:**
- `OVERVIEW.md` — Обзор проекта
- `QUICKSTART.md` — Быстрый старт
- `API.md` — Документация API
- `CHANGELOG.md` — История изменений
- `PLAN.md` — Общий план проекта

**Процедура для AI-ассистента:**

1. **НЕ создавайте** дополнительные файлы документации без явного разрешения
2. **ВСЕГДА спрашивайте** пользователя перед добавлением нового файла
3. **Предлагайте** структуру и назначение файла для обсуждения

**Примеры файлов, требующих уточнения:**
- `CONTRIBUTING.md` — правила контрибуции
- `ARCHITECTURE.md` — детальное описание архитектуры
- `DEPLOYMENT.md` — инструкции по развертыванию
- `TESTING.md` — документация по тестированию
- `FAQ.md` — часто задаваемые вопросы
- Любые другие специфичные для проекта документы

**Формат запроса уточнения:**

```
📋 Предложение по структуре документации:

Я считаю, что для проекта может потребоваться дополнительный файл:
- Название: ARCHITECTURE.md
- Назначение: Детальное описание архитектуры системы
- Причина: Проект имеет сложную структуру, которую сложно описать в OVERVIEW.md

Создать этот файл?
```

**Исключения:**

Следующие изменения **НЕ требуют** уточнения:
- Обновление содержимого стандартных файлов
- Исправление опечаток и ошибок
- Добавление примеров в существующие разделы

### Разделение плана и задач

Для всех проектов придерживайтесь следующего разделения:

- `PLAN.md` — общий план проекта, который ведёт AI-ассистент
- `workspace/tasks/tasks.md` — задачи разработчика, которые ведёт сам разработчик

AI-ассистент не должен смешивать эти два уровня в одном файле без явного указания пользователя.

### Расположение документации (по областям)

В проектах с модульной структурой документация разделяется по областям ответственности. Для единообразия используйте следующие расположения:

- `<project_name>/docs/` — документация проекта (общая архитектура, API, процессы)
- `<project_name>/<app_name>/docs/` — документация приложения-подмодуля (конкретная функциональность)
- `<project_name>/<app_name>/submodules/<submodule_name>/docs/` — документация вспомогательного модуля (git submodule) внутри приложения

Требования:
- Структура и стандарты в `docs/` идентичны для всех уровней (проект, приложения, вспомогательные модули)
- Поддерживайте актуальность ссылок между уровнями документации
- При наличии нескольких приложений/модулей — документируйте каждый независимо

## 📝 Стиль написания

### Форматирование

1. **Заголовки:**
   - Используйте иерархию `#`, `##`, `###`
   - Один H1 (`#`) на документ
   - Не пропускайте уровни заголовков

2. **Код:**
   - Используйте блоки кода с указанием языка: \`\`\`python
   - Для inline-кода используйте одинарные обратные кавычки: \`code\`
   - Добавляйте комментарии к сложным фрагментам

3. **Списки:**
   - Используйте `-` для ненумерованных списков
   - Используйте `1.` для нумерованных списков
   - Соблюдайте единообразие отступов

4. **Ссылки:**
   - Используйте относительные пути для внутренних ссылок
   - Добавляйте описательный текст для ссылок

### Язык и стиль

1. **Тон:**
   - Профессиональный, но дружелюбный
   - Избегайте жаргона без объяснений
   - Пишите простым языком

2. **Структура предложений:**
   - Короткие, ясные предложения
   - Один главный тезис на абзац
   - Используйте активный залог

3. **Термины:**
   - Используйте единые термины в рамках всей документации

## ✅ Чек-лист документации

Перед финализацией документации убедитесь:

- [ ] Все обязательные файлы созданы и заполнены
- [ ] Каждый раздел содержит конкретную информацию
- [ ] Нет устаревшей информации
- [ ] Используется единый стиль форматирования
- [ ] Все ссылки работают
- [ ] Документация легко читается и понятна
- [ ] Есть оглавление для больших документов

## 🔄 Поддержка документации

1. **Обновление:**
   - Обновляйте документацию вместе с кодом
   - Отмечайте изменения в CHANGELOG.md
   - Проверяйте актуальность примеров

2. **Обратная связь:**
   - Исправляйте неточности по мере их обнаружения
   - Дополняйте документацию на основе вопросов пользователей

## 📌 Дополнительные рекомендации

1. **Диаграммы и схемы:**
   - Используйте Mermaid для создания диаграмм в Markdown
   - Добавляйте визуализацию для сложных концепций

2. **Поиск и навигация:**
   - Создавайте содержание в больших документах
   - Используйте якори для ссылок внутри документа
   - Группируйте связанную информацию

---

**Помните:** Хорошая документация — это инвестиция в успех проекта. Она экономит время разработчиков и делает проект более доступным для новых участников и AI-ассистентов.
